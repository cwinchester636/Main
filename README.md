# SwapDeck

A mobile-first web app that helps trading card collectors (Pokémon, Magic: The Gathering, Yu-Gi-Oh!) find **mutual trades** with other collectors — instead of shipping costs, grading disputes, and marketplace scams.

You build two lists — **Haves** and **Wants** — and SwapDeck surfaces other collectors whose lists complement yours, prioritizing "perfect" matches where *they have what you want* **and** *you have what they want*.

This is a real, deployed full-stack app, not just a demo: a Cloudflare Worker + D1 database backend (`worker/`) behind a real (if lightweight) account system, and a React/Vite frontend (`src/`) served as static assets from its own Worker. There's no mock data left anywhere in the app — every account, collection, and match is a real row in a real database.

**Live right now:**
- Frontend: **https://swapdeck.cards** (custom domain; the `swapdeck.cwinchester636.workers.dev` fallback is disabled now that a custom domain is configured — see **Custom domain** below)
- API: **https://swapdeck-api.cwinchester636.workers.dev**

## How it works

- **Onboarding** — create an account with a username, email, and password (plus an avatar and optional ZIP code), or log in to an existing one. Creates a real account server-side and returns an auth token (stored only in this browser's localStorage — see **Accounts & auth** below).
- **My Collection** — search Pokémon, Magic: The Gathering, and Yu-Gi-Oh! and add results to your Have/Want lists. All three search the real, complete live card databases (see **Live card search**) and show a current market price next to the set/number for any live-sourced card (see **Live pricing**).
- **Matches** — a ranked list of other collectors, computed server-side. 🤝 "Perfect trade match" badges mean a trade needs no cash or shipping either way. Tap a match to see exactly which cards would change hands, then send a trade proposal.
- **Trades** — respond to (accept/decline) proposals you've received, and confirm proposals you've sent once the swap actually happens. See **Trades & verification** below.
- **Profile** — update your avatar/ZIP/search radius, or log out.

## Accounts & auth

Signing up requires a username, an email address, and a password — all three, not optional. Logging in works with either the username or the email, plus the password (`POST /api/login`). Session auth underneath is still the original bearer-token model: creating or logging into an account generates a random 256-bit token, and the frontend keeps the raw token in `localStorage`, sending it as `Authorization: Bearer <token>` on every request (see `src/api/client.js`) — password auth is the *gate* to getting a token, not a replacement for how requests are authenticated afterward.

**Password storage.** PBKDF2-SHA256 with a random 16-byte salt per account and 100,000 iterations (`worker/src/utils.js`'s `hashPassword`/`verifyPassword`), not a plain digest — unlike the 256-bit random session token (which has full entropy and can safely use one fast `SHA-256` pass), a human-chosen password can't, so it needs a slow, salted KDF. Comparison at login uses a constant-time check (`timingSafeEqual`) rather than `===`, so a wrong guess can't be timed character-by-character. Minimum length is 8 characters; there's no composition rule (no forced digit/symbol) — length matters more than composition, per current guidance (e.g. NIST 800-63B).

**Multiple sessions, stay signed in until you actually log out.** See **Session persistence** below — this used to be "one session at a time" (logging in on a new device silently signed you out everywhere else), which is no longer true.

**Email is collected and validated for shape only — not verified.** Signup checks the address looks like `x@y.z` and rejects anything else, but no confirmation email is ever sent, so there's no proof it actually belongs to whoever's signing up, and consequently **no password-reset-via-email either** (there's nothing to prove ownership of the inbox with). This is a deliberate, explicit scope cut for now: real verification needs a transactional email provider (API key, verified sending domain — infrastructure this project doesn't have yet), and shipping a "reset link" flow without real verification would be worse than not having one. See `worker/src/routes/accounts.js`'s `EMAIL_RE` comment.

**What actually improved over the old pure-token model:** losing your `localStorage` token, or switching devices, used to mean losing the account outright, with zero recovery path. Now the password *is* the recovery path — log in with username-or-email + password from anywhere, get a fresh token. **Accounts created before this feature shipped (including the 3 seed demo accounts) have no password set** and can only be reached through their original browser's stored token — the login form's error message is deliberately generic ("incorrect username/email or password") for both a wrong password and a real-but-passwordless account, to avoid leaking which case it is.

## Session persistence

Signing in stays signed in — indefinitely, on every device you've ever logged into, until you explicitly tap **Log out** on that specific device. No idle timeout, no forced re-login, no "logging in elsewhere signs you out here."

**One row per active login, not one token slot per account.** The original model (`accounts.token_hash`, a single `NOT NULL UNIQUE` column) meant every account could only ever have one valid token at a time — logging in on a second device silently overwrote and invalidated whatever token the first device was holding, which looked to that first device exactly like being logged out, with no warning. `sessions` (`worker/migrations/0022_sessions.sql`) replaces that: a `login` or `createAccount` call inserts a *new* row rather than overwriting anything, so a phone and a browser (or, during testing, several rebuilt app installs) can each hold their own independently valid session at the same time. `authenticate()` (`worker/src/auth.js`) now looks up the caller's token by joining through `sessions` rather than reading `accounts.token_hash` directly — that column still exists (SQLite can't drop a `NOT NULL UNIQUE` column without a full table-recreate migration, the same kind `0019_trade_status_cancelled.sql` did, not worth the risk for a purely cosmetic cleanup) but is never read for authentication anymore; `createAccount` still writes a throwaway value into it purely to satisfy the constraint.

**Logging out is the one thing that actually ends a session — and only that one.** `POST /api/logout` (`logOut`, `worker/src/routes/accounts.js`) deletes exactly the `sessions` row matching the caller's own current token, computed the same way `authenticate()` would (`getTokenHash`, shared between both). It never touches any of that account's other active sessions on other devices. The frontend calls this before clearing its own local token (`App.jsx`'s `logOut`) — best-effort: if the request fails (offline, etc.), the local session still clears immediately, since someone who tapped "Log out" should never be left looking logged in regardless of network state. Simply closing the app, or `localStorage` being cleared some other way, does **not** call this at all, and correctly leaves that session valid — reopening the app later just works, no re-login needed.

**Migrating existing sessions, not logging everyone out.** `0022_sessions.sql` backfills a `sessions` row from every existing account's `accounts.token_hash` in the same migration that adds the table — anyone already logged in when this shipped stayed logged in; the migration doesn't force a single re-authentication anywhere. Confirmed by direct query against this project's own local dev database (131 accounts accumulated across this whole session's testing, 131 sessions rows backfilled, exactly 1:1).

Deleting an account removes every `sessions` row for it (`deleteUser`'s cascade, `worker/src/routes/admin.js`) — every device that account was ever logged into loses access the moment the account itself is gone, regardless of how many sessions existed.

## Trades & verification

A trade proposal moves through a small lifecycle in `worker/src/routes/trades.js`:

1. **Pending** — proposer sends a proposal (`POST /api/trades`). The recipient sees it under Trades → Received.
2. **Accepted / declined / cancelled** — the recipient can accept or decline (`PATCH /api/trades/:id`); declining is terminal, and a new proposal can always be sent afterwards. Separately, **the proposer can cancel their own still-pending proposal** the same way (`action: "cancel"`) — see below.
3. **Completed** — once accepted, either side can tap "Mark trade as complete" (`POST /api/trades/:id/confirm`) after the swap actually happens in person or by mail. **This only flips the trade to "completed" once *both* people have confirmed** — one person tapping the button isn't proof anything happened, it's just a claim. Confirming is idempotent (tapping it twice does nothing the second time), and only the two participants can confirm at all.

**Cancelling is proposer-only and pending-only.** `respondToTrade` (`worker/src/routes/trades.js`) branches on `action: "cancel"` before any of the accept/decline logic runs: only `from_account_id` (the proposer, never the recipient — they have decline for that) can cancel, and only while `status` is still `'pending'` (403/error otherwise, mirroring accept/decline's own guards). It's deliberately **not** gated by `requireNotSuspended`, unlike accept/decline/confirm — withdrawing your own proposal is the opposite of trading, not an instance of it, so a suspended account can still cancel something it already sent before being suspended. The recipient gets notified either way (`notifyAccount`, "Trade cancelled"), the same as every other trade-lifecycle event. `'cancelled'` required widening `trade_proposals.status`'s CHECK constraint (`pending`/`accepted`/`declined` only, until now) — SQLite can't alter a CHECK constraint in place, so `worker/migrations/0019_trade_status_cancelled.sql` recreates the table with the wider constraint and copies every existing row across, the standard SQLite migration pattern for this kind of change.

There's no "undo a cancel" — once cancelled, a fresh proposal is the only way forward, same as declining.

**Either side can note a cash amount toward the trade, at their own step in the lifecycle** — the proposer at propose time (`cashAmount` on `POST /api/trades`), the recipient at accept time (`cashAmount` on `PATCH /api/trades/:id` with `action: "accept"`). Declining ignores any `cashAmount` sent with it — nothing to add cash to. **This is a noted amount only, never real money.** Nothing in this app moves funds between accounts — there's no payment processor, no escrow, nothing — the two people are expected to settle it themselves (cash, Venmo, whatever), same as they already coordinate shipping a card. Stored as `from_cash`/`to_cash` on `trade_proposals` (`worker/migrations/0010_trade_cash.sql`, `REAL` dollars — matching how a card's live price is already stored/compared everywhere else, not a new cents-based scheme for just this one field), validated non-negative server-side, and folded straight into the existing value-disparity check (`checkValueDisparity`'s `theirCash`/`yourCash` options in `src/utils/tradeValue.js`) — cash is exactly what closes the gap a card-only comparison would otherwise flag. Shown wherever a trade's cards are shown: `TradesView`, and the admin Trades view for dispute review.

`completed` isn't a value the `status` column can hold — the column's CHECK constraint (`pending`/`accepted`/`declined`) is intentionally left alone, since SQLite can't alter a CHECK constraint without recreating the table. Instead, "completed" is derived at read time from two nullable timestamp columns (`from_confirmed_at`, `to_confirmed_at`) both being set on an `accepted` row. See `worker/migrations/0002_trade_confirmations.sql`.

## Matching & proximity

Matching happens in `worker/src/routes/matches.js`: for each other account, it finds the overlap between their Haves and your Wants (and vice versa) using `game + lowercased name` as the identity key — not a shared card id, since cards can come from three different live APIs with no common id scheme.

**Real distance, when available.** On account creation and whenever a ZIP changes, the Worker geocodes it via [Zippopotam.us](https://www.zippopotam.us/) (free, keyless, server-side — same "free API, no key" pattern as the card search providers) and stores the ZIP centroid's `lat`/`lng`. When both sides of a potential match have coordinates, `worker/src/utils.js`'s `haversineMiles` computes real great-circle distance in miles, shown as e.g. "12.7 mi away". This is still centroid-based, not precise geolocation — no location-permission prompt, no device coordinates ever collected — so it's accurate to "which ZIP", not to the exact address.

**Search radius.** Profile has a "Search radius" setting (5/10/25/50/100/250 miles, or "Any distance" — the default). It's applied server-side in `getMatches`: a collector farther than your radius is dropped from *your* matches list (radius is per-viewer, not mutual — it never affects what you look like in anyone else's results). **A match is only ever filtered out when its distance is actually known.** If geocoding failed for either account (bad ZIP, Zippopotam down, no ZIP entered at all), that match's distance is `null` and it's always shown, radius setting or not — an infrastructure hiccup should never silently hide a legitimate match. Only a normal browser deploy's Worker has been used to test the actual Zippopotam call, since this sandbox blocks arbitrary outbound domains the same way it does for the card-search APIs (see **What's been verified vs. what hasn't**) — the surrounding filter/sort/graceful-degradation logic itself was fully verified locally by seeding known coordinates directly into D1 and exercising every path (in-radius, out-of-radius, radius removed, ZIP unchanged preserves coordinates, ZIP changed triggers re-geocode and nulls stale coordinates on failure) against the real Worker code.

**Fallback.** When distance can't be computed, the old ZIP-prefix bucketing still runs as a label: same ZIP ("Same ZIP code"), same first-3-digits ("Nearby (same area)"), or nothing. `distanceMiles` (when present) always takes priority over this in both sorting and display — see `src/utils/distance.js`.

## Live card search

Search results come from real, free, public card databases, queried directly from the browser (no extra backend hop, no API key):

- Pokémon → [Pokemon TCG API](https://docs.pokemontcg.io/)
- Magic: The Gathering → [Scryfall](https://scryfall.com/docs/api)
- Yu-Gi-Oh! → [YGOPRODeck](https://ygoprodeck.com/api-guide/)

These three were chosen specifically *because* they're free and CORS-enabled for direct browser use — no other trading card game has a comparable free public API, which is why the app is scoped to just these three (see `src/data/providers/`).

If a live API is unreachable, the picker shows a warning and falls back to a small curated catalog (`src/data/cards.js`) instead of breaking. If every provider fails, `useCardSearch` also `console.error`s each one's actual rejection reason (network error, HTTP status, CORS) rather than only surfacing the generic fallback message — this project's sandbox can't reach any of these three domains at all (confirmed directly, including from a real headless browser, not just `curl` — a genuine network policy, not a bug), so that's the only way a real failure gets diagnosed instead of guessed at.

**The Pokemon TCG API query was genuinely broken in production**, caught via that logging: `searchPokemonCards` was wrapping a wildcard inside quotes (`name:"char*"`), which isn't valid syntax for their query parser and reliably 500'd on every search. Fixed to the documented unquoted form (`name:char*`) — confirmed via a mocked-network test that the request URL now decodes to the correct query.

## Live pricing

Every live-sourced card shows its current TCGplayer-sourced market value next to its set and collector number (Pokemon TCG API's `tcgplayer.prices`, Scryfall's `prices.usd`, YGOPRODeck's `card_prices[].tcgplayer_price`) — no separate TCGplayer integration, just reading a field the search already fetched. This is one line, `CardMeta` (`src/components/CardMeta.jsx`), used everywhere a card is shown — the condition step's preview *as you're selecting it*, and every `CardChip` in Collection and Matches.

**The picker's search *results list* is the one exception — it shows set/number but never fetches a price**, via `CardMeta`'s `showPrice={false}`. This was a real production bug, not a design choice from the start: a live search can return dozens of rows (Pokemon up to 20, Scryfall's `unique=prints` often far more — every printing of a matching card, not just one row per card), and eagerly firing an individual price lookup for every row on every keystroke was flooding both APIs with enough concurrent per-card requests to get rate-limited or outright blocked, which is what "live search unavailable" actually was for a real user — see **What's been verified vs. what hasn't**. `useCardPrice`'s `enabled` option (`src/hooks/useCardPrice.js`) skips the fetch entirely, not just the display, so browsing results costs zero price requests; only an actually-selected or actually-saved card fetches one.

**How "live" it stays.** A price isn't stored anywhere — it never touches the backend or D1 at all. Each `CardMeta` (via `src/hooks/useCardPrice.js`) fetches it directly from the browser the moment the card renders, the same way search itself works. That means it's current as of whenever you're looking at it, not a snapshot from whenever the card was added — genuinely "most up to date," at the cost of a re-fetch (not a page-load-time value fixed in the database) every time you open Collection or Matches. Results are cached in memory for the rest of the tab session, so re-rendering the same card (e.g. switching tabs and back) doesn't re-request it — a fresh page load always gets a fresh price.

**Why this needed a schema change.** Once a card is saved to a Have/Want list, its `id` becomes the collection row's own id (stable — it's what "remove card" deletes by). The original live-search id (e.g. `live-pkmn-base1-4`, which a price lookup needs) is preserved separately as `sourceId` (`source_id` column, added in `worker/migrations/0004_collection_source_id.sql`) — `id` and `sourceId` deliberately serve two different jobs and are never conflated.

**Only real printings get a price.** Cards added from the curated fallback catalog (`data/cards.js`, used when a live search fails) aren't tied to a specific real printing, so `sourceId` is null for them and no price is ever fetched or shown — no API call wasted trying.

**Rate-limit awareness.** A Collection or Matches view can render many cards' worth of price lookups at once; `src/data/providers/priceQueue.js` caps it to 4 concurrent requests app-wide rather than firing them all simultaneously at these free, keyless services.

## Card condition

Adding a card to a Have/Want list is a two-step picker (`src/components/CardPicker.jsx`): pick the card, then record its condition, before it's actually saved. Five options, worst to best: **Heavily Played**, **Moderately Played**, **Lightly Played**, **Near Mint**, and **Graded** — picking Graded reveals a grade field (1-10) that has to be filled with a valid whole number before "Add to list" is enabled. Condition defaults to Near Mint (the common case) but nothing is saved until the second step is actually confirmed.

Both fields are optional at the database level (`condition TEXT`, `grade INTEGER`, added in `worker/migrations/0005_card_condition.sql`) — older collection items predate this feature and simply have neither. The two-column split (rather than folding a grade into the condition string) is because "graded" and "the grade itself" are different questions: SQLite can't express "grade is required only when condition = 'graded'" as a column-level CHECK constraint (it can't reference another column), so that cross-field rule is enforced in `worker/src/routes/collection.js` instead — condition must be one of the five values, and a grade outside 1-10 (or a graded condition with no grade at all) is rejected with a 400. A grade sent alongside a *non*-graded condition is silently dropped rather than rejected, since it's harmless leftover state, not a meaningful error.

**Note this doesn't adjust the live price.** A card's shown market value (see **Live pricing** above) is whatever baseline condition the source API returns — condition and price are recorded and displayed independently, not combined into one condition-adjusted number.

## Card verification photos

Adding a card to **Haves** is a three-step picker, not two: pick the card, record its condition, then take a photo of the actual card in hand — the third step can't be skipped, and "Add to Haves" stays disabled until a photo is attached. It's proof the card actually exists in the adder's possession, not just a claim; **Wants** never ask for one, since wanting a card isn't a possession claim. The photo is resized client-side (`resizePhoto` in `src/components/CardPicker.jsx`, canvas-based, capped at 1200px / JPEG quality 0.82) before upload — a phone camera capture can be several MB straight off the sensor, and a verification photo doesn't need that resolution. Capture itself is a plain `<input type="file" accept="image/*" capture="environment">`, which opens the camera directly on a phone browser and falls back to a normal file picker on desktop.

**Storage is Cloudflare KV (`env.PHOTOS`, `[[kv_namespaces]]` in `worker/wrangler.toml`), not R2.** R2 is the more natural fit for image blobs, but it needs a one-time opt-in from the Cloudflare Dashboard that nothing here can do via the API — R2 wasn't enabled on this account when this shipped, KV was available immediately with no setup. `collection_items.photo_key` (`worker/migrations/0008_card_photos.sql`) stores the KV key, never a public URL — nothing serves photos directly from KV. Add is `multipart/form-data`, not JSON, so the photo can travel in the same request as the card and condition (`worker/src/routes/collection.js`); deleting a collection item deletes its KV entry too (best-effort — an orphan just wastes a little storage, not worth failing the delete over). Binding a KV namespace for the first time worked against the existing `CLOUDFLARE_API_TOKEN` with no new permission needed — confirmed by the deploy log, not assumed (the "Workers Scripts: Edit" permission already listed under **Deploying** turned out to cover this; no fifth row needed in that table).

**Who can see a photo:** its owner, an admin, or someone who currently wants that exact card (`GET /api/collection/:id/photo`, `getCollectionItemPhoto` in `worker/src/routes/collection.js`) — i.e. it's showing up as a match for them, same `matchKey` logic used everywhere else a "does this count as the same card" question comes up. That's deliberately narrower than "anyone this account has ever matched with" — it's scoped to the specific card. The endpoint requires a bearer token, so nothing can be hotlinked as a plain `<img src>`; the frontend (`src/components/PhotoViewerModal.jsx`) fetches it as an authenticated blob and displays it via `URL.createObjectURL`, revoked on close. A camera-emoji button on `CardChip` (own Haves in Collection, matched cards in Matches) opens the viewer — it only renders when the card actually has a photo.

**A trade's card snapshot (see Admin trade visibility, under Admin below) carries the photo forward too** — an admin reviewing a dispute sees the actual verification photo each side had on file at propose time, not just the name/condition/grade. This needed its own independent copy of the photo bytes rather than reusing the live collection_item's KV key: a shared key would mean deleting the collection item (`deleteCollectionItem`) also deletes the trade's copy, which is exactly the kind of silent breakage a permanent record can't have. `worker/src/routes/trades.js`'s `copySnapshotPhoto` reads the live photo out of KV and writes it back under a new `snapshot/<id>` key at propose time — one extra KV read+write per photographed card offered, only at propose time, and the resulting `trade_snapshot_items.photo_key` (`worker/migrations/0009_trade_snapshot_photos.sql`) keeps resolving even after the original item is edited or deleted. Verified directly: proposed a trade, deleted the live collection item and confirmed its own photo endpoint now 404s, then confirmed the trade snapshot's photo still served byte-identical content.

## Value disparity warning

Committing to a trade (proposing one from Matches, or accepting one from Trades → Received) totals up the live market value of both sides first — what they'd be giving you against what you'd be giving them, using the exact same prices already shown on each `CardChip` (`src/utils/tradeValue.js`, `src/hooks/useCardPrice.js`'s shared cache, so it's never a different number than what's on screen). **If the two sides are more than 15% apart, a warning shows before anything is sent** (`ValueDisparityModal`) — both totals, the percentage gap, and a choice to cancel or proceed anyway. Nothing is blocked outright; this is a heads-up, not a rule.

"15% apart" is `(larger − smaller) / larger`, so a completely one-sided trade (one side priced at $0) always warns, and the two extremes only ever *widen* the warning, never suppress it. Cards with no resolvable live price (curated-catalog cards, or a provider that's down) simply aren't counted on either side — the comparison is honest about what's actually priced, never a guess dressed up as one. If *neither* side has any priced cards at all, there's nothing to compare and the trade proceeds with no popup, same as always.

**Why this needs `matches` in `TradesView`, not just `MatchesView`.** Proposing already has the two card lists in hand (`theyHaveYouWant`/`youHaveTheyWant`) from the match itself. Accepting doesn't — `GET /api/trades` was never extended with card data (a deliberate no-backend-change design: this is 100% client-side, reusing data the app already fetches) — so `App.jsx` now also passes its `matches` state into `TradesView`, which looks up the accepted trade's counterparty by account id to find the same two lists. If that lookup comes up empty (the overlap changed since the match was last computed, or matches hasn't loaded), accepting just proceeds without a check — consistent with the rest of the app's "never block on something we can't measure" posture (see **Matching & proximity**'s radius filtering and **Live pricing** above for the same principle applied elsewhere).

## Trade reports & chat

Each trade card (Trades tab, either direction, any status) has two footer actions: **💬 Chat** and **⚠️ Report an issue**.

**Chat** is a simple message thread scoped to that one trade — not a general DM system between arbitrary accounts (`trade_messages`, `worker/migrations/0011_trade_messages_and_reports.sql`). Either participant can post at any time regardless of the trade's status; there's no WebSocket/Durable Object infrastructure here, so `TradeChatModal.jsx` polls `GET /api/trades/:id/messages` every 4 seconds while open and stops when closed — proportional to this app's existing request/response architecture rather than a new real-time layer for one feature.

**Reporting** (`ReportTradeModal.jsx`, `POST /api/trades/:id/report`) lets either participant flag an issue with a trade — a reason from a fixed list (never received the card, not as described, no-show, cash not paid, other) plus optional free-text detail. **GPS location is requested only at the moment the report is submitted, never ambiently for ordinary trades** — a deliberate privacy choice: nothing about a normal trade going fine ever touches the Geolocation API. Declining the location prompt still lets the report through with `lat`/`lng` left null; the request races the browser's own `timeout` option against an independent JS timer (`src/utils/geolocation.js`) rather than trusting that option alone — testing turned up a real case (this sandbox's headless browser, though nothing guarantees a real device never does the same) where `getCurrentPosition` hung well past its stated timeout, which would otherwise have stuck the whole report submission.

**Admin sees reports at Admin → Reports** — every report, open ones first, each with the reporter, reason, description, a Google Maps link when a location was captured, and a **View chat log** button. That button is what "admins should have access to chat logs" actually means here: **admin can read a trade's chat only while that trade has at least one *open* report** (`hasOpenReport` in `worker/src/routes/reports.js`, re-checked on every request — not a one-time flag), never for an ordinary trade nobody's flagged, and resolving every open report on a trade closes that access again immediately. Admin can read but never post into a chat log (enforced server-side in `sendMessage`, regardless of what the UI shows). This was a deliberate scope decision, not the only reasonable one — the alternative (admin can read any trade's chat at any time, matching how admin already sees every trade's cards/cash/photos) was explicitly considered and rejected in favor of gating chat specifically to actual disputes, since a private conversation is more sensitive than structured trade metadata.

## Ratings & suspension

Once a trade is `completed` (both sides confirmed — see **Trades & verification**), either participant can leave the other a thumbs-up/thumbs-down rating with a comment (`RateTradeModal.jsx`, `POST /api/trades/:id/rating`, `trade_ratings` table in `worker/migrations/0012_ratings_and_suspension.sql`). Rating a trade that isn't completed yet, or one you weren't a party to, is rejected server-side (400/403) regardless of what the UI shows. It's an upsert, not a one-shot: rating the same trade again (`ON CONFLICT(trade_id, rater_account_id) DO UPDATE`) revises your existing rating in place rather than erroring or stacking a duplicate — someone can change their mind after a slow resolution instead of being stuck with a first impression forever.

**A thumbs-down requires a comment; a thumbs-up doesn't.** A negative rating with no accountability attached to it is just noise nobody can act on, so `rateTrade` rejects (400) `thumbsUp: false` unless `comment` is present and non-blank after trimming — whitespace-only doesn't count. Enforced server-side regardless of the UI; the modal mirrors it client-side too (the comment field relabels itself "required for a bad trade," the submit button stays disabled until something's typed, same as any other required field elsewhere in this app).

**The visible number is a plain percentage, not a weighted or decaying score:** `positivePct` = thumbs-up ÷ total ratings received, computed fresh from `trade_ratings` on every request (`getRatingSummaries` in `worker/src/routes/ratings.js`, one batched `GROUP BY` query rather than N+1 — used everywhere a rating shows: Matches, Trades, and both Admin Users and Admin Trades). `RatingBadge.jsx` shows "No ratings yet" at zero ratings rather than a misleading 0%/100%, and a badge already visible on a trade card doesn't refresh itself the instant you submit a rating on that same trade — it catches up on the next full data reload (`loadEverything`), the same staleness tradeoff every other summary in this app already has.

**Suspension is a manual, admin-only switch — never automatic off a rating or report threshold**, the same reasoning already established for fraud reports requiring human review before any consequence: a coordinated pile-on of false-negative ratings (or reports) shouldn't be able to take down an innocent account with no person ever looking at it. It's a nullable timestamp, not a boolean (`suspended_at` on `accounts` — null means never suspended, a value means suspended and since when), the same convention as `resolved_at`/`from_confirmed_at` elsewhere in this schema. Admin toggles it per-user from Admin → Users (`PATCH /api/admin/users/:id/suspend`, `setUserSuspended` in `worker/src/routes/admin.js`) — suspending asks for confirmation first, unsuspending doesn't. An admin can't suspend their own account (400) — the same accident-prevention guardrail as the existing can't-delete-self check, not a real security boundary.

**What suspension actually blocks, precisely:** a suspended account can still log in, see `GET /api/me`, and add/remove/view collection items — nothing about `authenticate()` itself changes. What's blocked is proposing a trade, accepting/declining one, confirming one, and sending a chat message — each of those four handlers calls a shared `requireNotSuspended` guard (`worker/src/utils.js`) as the very first thing they do, before any other validation, so the block applies immediately to trades already in progress, not just new ones. `proposeTrade` also rejects (403) if the *recipient* is suspended, not just the proposer, and `getMatches` excludes suspended accounts from every other user's results entirely — surfacing someone as a match you can never actually trade with would be misleading. The frontend mirrors all of this: a global banner on every tab while suspended, the Accept/Decline and "Mark trade as complete" buttons hidden on trade cards, and the chat composer replaced with an explanatory message (`composeDisabledMessage` on `TradeChatModal.jsx`) — but every one of those is a UI convenience, not the actual enforcement; a direct API call is what the four guarded handlers above actually stop. Rating a trade and viewing your collection are deliberately *not* gated by suspension anywhere, matching "they can still log in and manage their collection/wants but that is it."

Deleting a suspended (or any) user cleans up their `trade_ratings` rows the same explicit-cascade way as every other trade-scoped table — see **Admin**'s cascade-delete note below, which now also covers this one.

## Push notifications

Opt-in browser push (Profile → Notifications) for the five events someone can't otherwise find out about without opening the app: a new match, a new trade proposal, your proposal being accepted, a trade you're in becoming fully confirmed, and a new chat message. Built on the standard Web Push API (`PushManager.subscribe`) and a bare service worker (`public/sw.js`) that does nothing but show a notification on a `push` event and focus/open the app on click — no offline support, no asset caching, that's not what it's for here.

**Sending uses `@block65/webcrypto-web-push`, not the `web-push` npm package.** `web-push` leans on Node's `crypto` module directly, which doesn't exist in the Workers runtime; this library does the same RFC 8291 (`aes128gcm` payload encryption) and RFC 8292 (VAPID JWT auth) work using only standard WebCrypto (`crypto.subtle`), which Workers, like every other modern JS runtime, actually has. `worker/src/push.js` is the whole integration: `buildPushPayload(message, subscription, vapid)` does the crypto, the result is `fetch`-ready, `fetch(subscription.endpoint, payload)` sends it.

**The VAPID keypair is a real one-time setup step, not baked into the app.** The public half lives in `wrangler.toml` as a plain var (`VAPID_PUBLIC_KEY`, safe to commit — it's handed to every subscribing browser) and is mirrored into the frontend build as `VITE_VAPID_PUBLIC_KEY` in `.env`; both must be the exact same key or subscribing fails. The private half is a Worker secret, `worker/wrangler.toml` never sees it — `.github/workflows/deploy-worker.yml`'s "Set VAPID private key secret" step runs `wrangler secret put` from a `VAPID_PRIVATE_KEY` repo secret on every deploy (idempotent, and skipped harmlessly by its own plain-bash `if [ -n "$VAPID_PRIVATE_KEY" ]` check until that repo secret actually exists — see **Deploying** for why that's a shell check rather than a workflow-level `if:`). **This repo secret has not been added yet** — until it is, `notifyAccount` (`worker/src/push.js`) sees `env.VAPID_PRIVATE_KEY` unset and silently no-ops on every trigger, so the rest of the app is completely unaffected by push not being configured; subscribing itself still works and just won't result in any notification arriving. Add it once at Settings → Secrets and variables → Actions → **New repository secret**, name `VAPID_PRIVATE_KEY`, using the value generated for this deployment (shared once, out of band, when this feature was built — not committed anywhere in this repo).

**Notifications are fire-and-forget and never load-bearing.** Every trigger site (`proposeTrade`/`respondToTrade`/`confirmTrade` in `worker/src/routes/trades.js`, `sendMessage` in `worker/src/routes/messages.js`) wraps its `notifyAccount` call in `ctx.waitUntil()` — the Worker's `fetch` handler had to start taking a third `ctx` parameter for this, previously unused — so the actual trade/message action's response is never delayed by, or made to fail because of, a push send. Inside `notifyAccount`, each subscription is sent to independently (`Promise.allSettled`, one broken subscription can't stop another's), every failure is caught and just logged, and a `404`/`410` response (the push service's way of saying that endpoint is gone for good — RFC 8030 §7.3) deletes that subscription row so it stops being retried forever. Each `fetch` to the push service also races a 10-second `AbortSignal.timeout` — confirmed in testing that an unreachable endpoint can hang far longer than that instead of failing fast, the same failure mode already hit and fixed for Geolocation (see **Trade reports & chat**), so the same fix applies here: one slow/dead subscription must never hold the whole `ctx.waitUntil()` open indefinitely.

**Unsubscribing is two-sided.** Turning notifications off in Profile calls the browser's own `PushSubscription.unsubscribe()` *and* tells the backend to drop that subscription row (`POST /api/push/unsubscribe`, scoped to the caller's own account — you can't guess someone else's endpoint to unsubscribe them). Deleting an account drops all of its subscription rows too, the same explicit-cascade way as every other account-scoped table (see **Admin**'s cascade-delete note).

**New-match notifications are the one trigger that isn't a single obvious event — they need to tell a genuinely new match from one that's just still there.** Matches were never stored (`getMatches` always recomputed live from `collection_items` — see **Matching & proximity**), so there was nothing to diff a "before" against. `known_matches` (`migrations/0014_known_matches.sql`) fixes that: one row per account pair that's ever matched, canonical-ordered (the lexicographically smaller id always goes in `account_id_a`, enforced by a `CHECK` constraint, not just application code) so a match is naturally one row rather than two directed ones. Every `addCollectionItem` call — adding a have *or* a want, either can create a new overlap — runs `notifyNewMatches` (`worker/src/routes/matchAlerts.js`, also under `ctx.waitUntil()`) afterward: recompute the account's current matches (`computeMatches`, factored out of `getMatches` in `worker/src/routes/matches.js` so both share one definition of "what counts as a match"), diff against `known_matches`, and for any pair not already known, insert it and notify *both* sides. Removing an item never runs this — deleting a card can only ever remove a match, never create one, so there's nothing new to tell anyone about. Deliberately, `known_matches` rows are never deleted when a match later disappears (say, the overlapping card gets removed): if it reappears later, this stays quiet rather than re-notifying — the same "under- rather than over-notify" bias as every other push trigger in this app, and simpler than tracking exactly when a match transitions from gone to back.

**Reading the actual comments behind a rating is "on request," not shown inline everywhere.** `RatingBadge` now optionally takes an `onClick` and renders as a real `<button>` when it's supplied (`GET /api/accounts/:id/ratings`, `getRatingsForAccount` in `worker/src/routes/ratings.js`, open to any authenticated caller — same visibility as the percentage itself, and each entry includes the rater's username rather than being anonymous, so a review is attributable the same way the percentage already implicitly is). Clicking it opens `RatingsListModal.jsx`: every rating for that account, newest first, thumbs-up/down, the rater, the date, and the comment when there is one. Wired in everywhere a `RatingBadge` already showed a percentage — Trades (the counterparty's badge, no layout change needed, `trade-card-header` was already a plain `<div>`), Admin (Users list and the admin Trades view, both sides), and Matches, where it needed a small structural workaround: the whole match-card summary row is itself a `<button>` (the expand/collapse toggle), and a `<button>` can't nest inside another `<button>` — valid HTML doesn't allow it, and behavior across browsers is inconsistent if you try. So the clickable badge lives in the *expanded* match detail instead (a plain `<div>`, no nesting issue), as a second "tap to read reviews" line rather than making the always-visible summary-row badge itself clickable.

## Local events

A user-submitted calendar (Events tab) for local card events — tournaments, releases, meetups — rather than pulling from a real external events API. That's a deliberate choice, not a shortcut: unlike card search/pricing (Scryfall, the Pokémon TCG API, YGOPRODeck — all real, free, public, and already integrated), there's no equivalent free public API for "local TCG events near a ZIP code." Wizards/Pokémon/TCGplayer all have their own store/event locators, but none expose one as an open API this app could pull from, so the only honest options were user-submitted or nothing. Anyone can post an event (`POST /api/events`): title, ZIP, date/time, and optional location name, description, and link. Any participant (or an admin) can remove one they posted; deleting an account cleans up its events the same explicit-cascade way as everything else (see **Admin**'s cascade-delete note). Posting isn't suspension-gated — suspension's documented scope is trading and messaging specifically (see **Ratings & suspension**), and telling people about a local event is neither.

**Browsing reuses the exact distance/proximity math `getMatches` already has**, not a second implementation: `listEvents` (`worker/src/routes/events.js`) geocodes the event's ZIP the same way `createAccount`/`updateMe` already geocode a person's own (`geocodeZip`, `worker/src/geocode.js`), then filters and sorts with the identical `haversineMiles`/`zipProximity` pair from `worker/src/utils.js` — an event with no resolved coordinates, or belonging to a caller with none, is never hidden just because distance can't be confirmed, the same "unknown is never treated as out of range" rule **Matching & proximity** already documents.

**Posting a new event pushes a real-time alert to everyone nearby with notifications on** (`notifyNearbyAccounts` in `worker/src/routes/events.js`, under `ctx.waitUntil()` like every other push trigger — see **Push notifications**), but "nearby" is deliberately *not* the same radius semantics as browsing. A person who left their matching radius at "any distance" almost certainly meant that for trading, where shipping makes distance mostly beside the point — it doesn't follow that they want to be woken up for an event on the other side of the country, where physically showing up is the entire premise. So while *browsing* the Events list still honors an explicit "any distance" setting with no cap, the *notification trigger* falls back to a fixed 50-mile default (`DEFAULT_NOTIFY_RADIUS_MILES`) whenever `radius_miles` is null, and only fires at all when the event's own ZIP actually geocoded — with no coordinates to measure from, there's no way to confirm anyone's really "in the area," and guessing wrong means spamming people with an irrelevant alert. The event still gets saved and is still findable by browsing either way; a failed geocode just means it can't proactively notify anyone. Suspended accounts are deliberately *not* excluded from event notifications (unlike matches, which do exclude them) — a suspension blocks trading and messaging specifically, not knowing what's happening at the local shop.

**RSVPs are a plain toggle, not a push trigger.** `POST /api/events/:id/rsvp` (`toggleRsvp`) flips the caller's own `event_rsvps` row on or off and returns the new `going`/`rsvpCount`; the creator is auto-RSVP'd at creation time (`createEvent` inserts both rows in the same request), since a brand-new event showing "0 going" including its own organizer would be an odd first impression. Deliberately, RSVPing never notifies the event's creator — a popular event getting one push per RSVP is exactly the over-notify failure mode this app has consistently avoided everywhere else (see **Push notifications**' new-match diffing and events' own 50-mile default, both built the same way). Counts are batched across an entire events list in one pair of queries (`getRsvpInfo`), not one query per event, the same N+1-avoidance pattern `getRatingSummaries` already established. Deleting an event explicitly deletes its `event_rsvps` first (D1 doesn't enforce the `ON DELETE CASCADE` foreign key any more than anywhere else in this schema); deleting an *account* has to clear `event_rsvps` two separate ways — the account's own RSVPs to anyone's events, and, before its own posted events are deleted, every RSVP anyone *else* left on those — otherwise the second case would orphan the moment the event row under it disappears.

## Notifications inbox

Every push trigger this app has (new match, trade proposal/acceptance/completion, new message, local event) also writes an in-app row via the same call, `notifyAccount` (`worker/src/push.js`) — unconditionally, before it even checks whether a VAPID key is configured or the account has any push subscription at all. That's deliberate: push can be missed (permission never granted, notification dismissed, phone off, browser closed) or simply never turned on, and someone in any of those states still needs somewhere to see what happened. The bell icon in the app header (every tab, not just one) shows an unread count and opens `NotificationsModal.jsx`; each entry that came from a specific event (`linkTab` — `'trades'`, `'matches'`, or `'events'`) is tappable and jumps straight to that tab. Opening the inbox marks the whole list read in one request (`PATCH /api/notifications/read`) rather than per-item — "I looked at the list" is a reasonable definition of "seen" for a one-way activity feed, the same convention most notification inboxes use. The list itself is capped at the 50 most recent rather than paginated — plenty for what's meant to be a recent-activity feed, not a permanent archive. Deleting an account clears its `notifications` rows the same explicit-cascade way as everything else (see **Admin**'s cascade-delete note).

## Blocking

Self-service, no admin involved — the previous only way to stop someone from repeatedly proposing trades or messaging you was asking an admin to suspend their entire account, which is disproportionate for a single bad interaction. A "🚫 Block {username}" button lives wherever you already see someone else's identity: the expanded Matches detail (placed there rather than the summary row, for the same nested-`<button>`-invalidity reason the ratings badge already documents — the summary row is itself a toggle `<button>`) and the trade-card footer actions in Trades. Both confirm before acting (`window.confirm`) and call the same shared handler.

**One directed row, two-sided effects.** `account_blocks` (`worker/migrations/0018_account_blocks.sql`) stores who blocked whom — `blocker_account_id`, `blocked_account_id`, unique per pair — but every place that *consumes* it treats a block as mutual: `isBlockedEitherWay` (`worker/src/routes/blocks.js`) checks both directions with one query, and it's what `proposeTrade` calls before creating a new proposal, and what `computeMatches`'s `others` query excludes via a `NOT IN (...UNION...)` subquery on both directions. The person who got blocked has no way to tell *they're* the one who got blocked rather than the other way around — the propose-trade rejection is the same neutral message either way (`"this collector isn't accepting new trades from you right now"`, 403), and they simply stop showing up as a match, no different from any other match disappearing.

**Blocking retroactively clears pending trades, both directions.** `toggleBlock` (`POST /api/accounts/:id/block`, same endpoint toggles on and off) inserts the block row and auto-declines any still-`pending` trade proposal between the two accounts — whichever side proposed it — in the same `env.DB.batch()`, so a block can't be routed around by an already-outstanding proposal. Self-blocking (400) and blocking a nonexistent account (404) are both rejected before anything is written. Unblocking is the same endpoint called again (toggle, not a separate unblock route) and only removes the block row — it doesn't restore whatever trade got auto-declined or bring back a match that's since drifted apart for unrelated reasons (cards changed in the meantime, etc.); matches just get recomputed fresh either way.

**Blocked users are listed and reversible from Profile** (`GET /api/blocked`, `listBlocked`), a "Blocked users" section that only renders once the list is non-empty, each row with a one-tap "Unblock" calling the same toggle handler. Deleting an account clears every `account_blocks` row naming it, either as blocker or as the one blocked, the same explicit-cascade way as everything else (see **Admin**'s cascade-delete note, which now also covers this one).

## Pro tier / paywall

SwapDeck Pro is a paid tier, built as groundwork for real in-app purchases (see **Mobile app (Capacitor)**) — Apple/Google both require their own billing (StoreKit / Play Billing) for anything sold inside a native app, which needs a real native app to exist before it's worth wiring up. This is the entitlement side of that: what Pro actually unlocks, enforced server-side, with a working paywall UI — real billing is a separate, later step (see "How someone actually becomes Pro today" below).

**What's gated, and the free-tier limits:**

- **Collection size** — 25 cards each in Haves and Wants (`FREE_COLLECTION_LIMIT`, `worker/src/utils.js`). Enforced in `addCollectionItem` (`worker/src/routes/collection.js`): a free account at the cap gets a 403 with an upgrade message before any photo upload work happens, not after. Removing a card to make room always works regardless of tier — this only blocks *growing* past the limit, never shrinks an existing over-limit collection (there's no reason to be destructive about it, and someone who was Pro and lapsed keeps whatever they already had).
- **Search radius** — free accounts are capped at 5 miles (`FREE_MAX_RADIUS_MILES`); every wider option (10/25/50/100/250 miles) and "Any distance" are Pro-only, effectively "worldwide" once unlocked. Enforced in both `createAccount` and `updateMe` (`worker/src/routes/accounts.js`) — a fresh signup defaults to the 5-mile cap now, not "any distance" like it did before Pro existed (a real gap caught in testing: the old default silently gave every new account unlimited radius, bypassing the whole point of the limit).
- **Push notifications** — Pro-only, enforced in `subscribe` (`worker/src/push.js`): a free account's `POST /api/push/subscribe` is rejected outright before it ever creates a subscription row. Deliberately doesn't touch the in-app notifications inbox at all — `notifyAccount` still writes there unconditionally for everyone regardless of tier (see **Notifications inbox**), so nobody on the free tier misses out on knowing what happened, just on being proactively pinged about it.
- **A cosmetic "⭐ Pro" badge** next to your name — Profile (your own), Matches, Trades, and Admin's Users/Trades views, wherever someone's username already shows.

**One nullable timestamp, not a boolean.** `accounts.pro_until` (`worker/migrations/0020_pro_tier.sql`) follows the same convention as `suspended_at` elsewhere in this schema: null means never/no-longer Pro, a future timestamp means active Pro until then, and a past timestamp lapses on its own — `isPro(row)` (`worker/src/utils.js`) is just `pro_until > Date.now()`, no separate expiry job needed. Included as `isPro` on every account shape the API already returns an account through — `getMe`/`login`/`createAccount`/`updateMe` for your own account, and the counterparty/other-account shapes in `getMatches`, `getTrades`, and both Admin list endpoints (each of those needed `pro_until` added to their existing joined queries, the same way `isSuspended` already was).

**The paywall itself never blocks silently — every gate that can be hit pre-emptively is, with a specific reason.** `PaywallModal.jsx` is one reusable component (perks list + a `reason` line) opened from four places: Collection's "+ Add Card" button turns into "🔒 + Add Card" and opens the paywall instead of the picker once a list is at the cap (checked client-side against the same `FREE_COLLECTION_LIMIT` the server enforces, purely so the UI doesn't need to fire a request just to find out); Profile's radius `<select>` labels every locked option "(Pro)" and, if one is picked anyway, opens the paywall and reverts the selection rather than silently clamping it or letting a doomed save request go out; Profile's Notifications section swaps the "Enable notifications" button for a locked explanation once `!account.isPro`; and Profile has a standing "Your plan" section (free accounts only) with a "See Pro benefits" button as a non-triggered entry point. All four are client-side conveniences — the server enforces every one of these independently and would reject the request regardless of what the UI shows, the same "never trust the client alone" posture as every other gated action in this app.

**Two ways to become Pro: a real purchase (see below), or an admin grant.** `PATCH /api/admin/users/:id/pro` (`setUserPro`, `worker/src/routes/admin.js`) sets `pro_until` to one year out (or `null` to revoke), admin-only, mirroring `setUserSuspended`'s exact shape — a deliberate, honest fallback for support/comping/testing that exists independently of real billing. The admin grant's one-year expiry is itself deliberately a real timestamp rather than a permanent flag, so it can't be mistaken for one alongside the real purchase path's actual lifetime grant (see **In-app purchases**). Admin's Users list shows a "Grant Pro"/"Revoke Pro" button next to Suspend, same interaction pattern.

Deleting an account needs no extra cascade-delete work for this feature — `pro_until` is a plain column on `accounts` itself, not a separate table, so it's removed automatically with the account row.

## In-app purchases

SwapDeck Pro is a real, one-time (non-subscription) $1.99 purchase on Android, via [RevenueCat](https://www.revenuecat.com/) — chosen over talking to Google Play Billing directly because it handles receipt validation and cross-store purchase state itself, which otherwise means implementing the Google Play Developer API's own server-side verification by hand. The code side is complete; what's still outstanding is entirely external account setup (see the checklist below) that only the account owner can do from Google Play Console and RevenueCat's own dashboards.

**The purchase flow, end to end:** `PaywallModal.jsx` shows a real "Buy Pro — $1.99" button (`src/utils/purchases.js`'s `isPurchasingSupported()` gates this to the native Android app specifically — `Capacitor.isNativePlatform()` plus a configured `VITE_REVENUECAT_PUBLIC_KEY` — the website itself still shows "Purchasing is only available in the SwapDeck Android app right now," since there's no store to buy through from a browser tab). Tapping it calls `Purchases.purchasePackage()` (the `@revenuecat/purchases-capacitor` SDK), which opens Google Play's own native purchase sheet. `Purchases.configure()` is called with `appUserID` set to this exact SwapDeck account's own `id` — not left to RevenueCat's default anonymous id — specifically so the backend can look the same purchase back up by that id with no separate mapping table needed.

**The client's own "purchase succeeded" claim is never trusted alone.** Once `purchasePackage()` resolves, the client calls `POST /api/me/pro/verify` (`verifyProPurchase`, `worker/src/routes/purchases.js`), which independently re-checks the purchase against RevenueCat's own server — `GET https://api.revenuecat.com/v1/subscribers/:accountId` using a secret API key (never the public key the client SDK uses) — and only sets `pro_until` if that lookup confirms an active `pro` entitlement. This is the same "server enforces it, client is just a convenience" posture as every other gate in this app, applied to the one place getting it wrong would actually cost money. A one-time purchase grants a 100-year `pro_until` (`LIFETIME_MS` in `purchases.js`) — long enough to be permanent in practice, while staying a real timestamp on the same column the admin-grant path already uses, not a second "is this forever" flag to keep in sync.

**The secret key needed for that server-side check is a Worker secret, following the exact same one-time setup pattern as `VAPID_PRIVATE_KEY`** (see **Push notifications**): `.github/workflows/deploy-worker.yml`'s "Set RevenueCat secret key" step runs `wrangler secret put` from a `REVENUECAT_SECRET_KEY` repo secret on every deploy, idempotent, and skipped harmlessly by its own plain-bash check until that repo secret exists — **not yet added**, so `verifyProPurchase` currently returns a 503 ("Pro purchases are not fully configured yet") rather than crashing or, worse, silently granting Pro without ever actually checking anything. Confirmed by testing both failure paths directly: with no secret configured at all (503, `isPro` correctly still `false` afterward), and separately with a fake secret key against RevenueCat's real API — unreachable from this sandbox the same way `dl.google.com` and the live card-search APIs already are (see **What's been verified vs. what hasn't**) — which correctly returns a 502 ("could not verify... try again") rather than hanging, confirming the network-failure path is safe too, not just the not-configured one.

**What's genuinely outstanding — external account setup, not code, and only the account owner can do it:**

1. **Google Play Console**: create the app listing (package name must be exactly `cards.swapdeck.app`, matching `capacitor.config.json`) if it isn't already there, and upload at least one build to an internal testing track — Play Console won't let in-app products go live against an app with no build uploaded at all.
2. **Google Play Console → Monetize → Products → In-app products**: create a one-time **managed product** (not a subscription) with a product ID (e.g. `swapdeck_pro`) and set its price to **$1.99** — the price point that nets at least $0.99 after Google's cut (30% standard, 15% once qualifying for the reduced-fee tier) regardless of which rate ends up applying.
3. **A free [RevenueCat](https://app.revenuecat.com/) account**, with a project connected to the Play Console app above (RevenueCat's setup flow asks for a Google Play service-account JSON with the right permissions — generated from Play Console's API access settings).
4. **In RevenueCat**: create an **Entitlement** with identifier `pro` (matching `PRO_ENTITLEMENT_ID` in `src/utils/purchases.js` and the default `REVENUECAT_PRO_ENTITLEMENT_ID` fallback in `worker/src/routes/purchases.js`), an **Offering** with a **package** of type **Lifetime** (RevenueCat's type for a non-renewing one-time purchase, not a subscription duration) pointing at the `swapdeck_pro` product from step 2, and mark that offering **current**.
5. Grab RevenueCat's **public API key** (Android) and add it as `VITE_REVENUECAT_PUBLIC_KEY` in `.env` — safe to commit, same reasoning as `VITE_VAPID_PUBLIC_KEY` above it.
6. Grab RevenueCat's **secret API key** and add it as a `REVENUECAT_SECRET_KEY` **repository secret** (Settings → Secrets and variables → Actions → **New repository secret**) — never committed, picked up automatically by the next deploy.
7. Rebuild the Android app (`npm run cap:sync`, then Run/Build APK from Android Studio — see **Mobile app (Capacitor)**) so it picks up the new `VITE_REVENUECAT_PUBLIC_KEY`.

Once all seven are done, a real device purchase — including Google Play's sandbox/license-tester purchases, which don't charge real money — should flow end-to-end through code that's already written and, as far as this sandbox can verify, correct.

## Referrals

Refer a friend, and when they complete their first positively-rated trade, **both of you get a free month of Pro** — deliberately a guaranteed reward for a real, verifiable action rather than any kind of chance-based prize. That distinction matters beyond just product design: a chance-based reward tied to payment is legally a lottery/raffle in most U.S. states and needs a gaming license; a deterministic reward for a real action a person actually completed is not, which is exactly why this app's earlier sweepstakes idea got redesigned around Pro-as-referral-incentive instead of Pro-gated-chance-of-a-prize.

**No separate invite-code scheme — the referral code is just the referrer's own username.** One less id to generate, store, or keep in sync with anything. `Onboarding.jsx`'s signup form has a "Referred by" field, pre-filled from a `?ref=username` URL parameter if the signup page was opened via a shared invite link (`https://swapdeck.cards/?ref=someusername`) but always manually editable too — someone told a friend's username in person can type it in exactly as easily as someone who tapped a link. Profile's "Invite friends" section generates that link and shares it via the OS-native share sheet (`navigator.share`, which works identically on the website and inside the Capacitor WebView on Android with no extra plugin) or falls back to copying it to the clipboard where `navigator.share` isn't available (most desktop browsers).

**Fraud prevention happens once, silently, at signup — never at reward time, and never by blocking the signup itself.** `resolveReferrer` (`worker/src/routes/accounts.js`) runs two checks before recording `referred_by_account_id`, both explained in more depth in its own comments:

1. **Same signup IP as the referrer** (`request.headers.get('CF-Connecting-IP')`, Cloudflare's own edge-verified client IP header — not something a client can spoof) — most likely the same person signing up twice from their own device to farm the reward.
2. **The same Gmail mailbox as the referrer, or as an already-referred sibling, via the dot/`+` trick** (`normalizeEmailForFraudCheck`, `worker/src/utils.js`) — Gmail ignores dots in the local part and anything after a `+`, so `name@gmail.com`, `n.a.me@gmail.com`, and `name+ref2@gmail.com` all deliver to one real inbox, a well-known way to make one person's signups look like distinct "friends." Deliberately Gmail-only — other providers don't reliably share either convention, and normalizing one that treats dots as significant would falsely collide two genuinely different mailboxes.

Neither check blocks the signup itself if it fails — a bad-faith or merely coincidental match just means no referral gets recorded, silently, the same "never let a fraud check turn into a support ticket for an innocent person" instinct behind every other guard in this app. Neither is foolproof (two real devices and two real mailboxes defeat both), but both raise the cost of casual self-referral abuse well past what someone would bother with for a free month of Pro.

**The reward itself fires from `rateTrade`** (`worker/src/routes/ratings.js`), the instant a `thumbsUp: true` rating lands on a completed trade, if the *rated* account (not the rater) was referred and hasn't already been paid out (`referral_reward_granted_at IS NULL`, a one-time gate). **One more fraud check happens here, not at signup:** the rater can't be the referred account's own referrer. Without this, a referrer and a single account they refer could complete a fake trade with each other and rate each other positively, collecting the reward with no real third party involved at all — requiring the positive rating to come from someone else forces at least one additional real (or additionally fake) account into any attempt. `extendPro` adds `REFERRAL_REWARD_DAYS` (30) to whichever is later, the account's current `pro_until` or now — an already-Pro account's time is extended, never shortened or overwritten. Both sides get an in-app notification either way (`notifyAccount`, same as every other push trigger in this app).

**The referrer's own payout is capped lifetime at `REFERRAL_REWARD_CAP` (12)** — a `referral_rewards_granted` counter on their own account row, checked before each grant. The referred side's one-time welcome reward is never capped, since by definition each new person can only trigger it once regardless of who referred them; the cap exists specifically to bound how much *one* referrer can keep earning, as a ceiling on worst-case abuse the two signup-time checks above didn't catch, not a replacement for them.

Deleting a referrer account clears `referred_by_account_id` on every account it points to (set to `null`, not deleted — the referred accounts are real, separate accounts and stay) as part of `deleteUser`'s existing explicit-cascade batch, the same "D1 doesn't enforce `ON DELETE SET NULL`, so do it explicitly" reasoning as everything else in that cascade.

## Admin

An Admin tab (visible only to admins — it's not in the bottom nav at all for anyone else) has three sub-views. **Users**: lists every account, oldest first, shows each one's rating badge, and can suspend/unsuspend (see **Ratings & suspension**) or permanently delete one — `GET /api/admin/users`, `PATCH /api/admin/users/:id/suspend`, `DELETE /api/admin/users/:id`. **Trades**: lists every trade proposal ever made, newest first, with both parties' username/email, every timestamp (proposed, each side's confirmation, completed), and the cards each side offered — `GET /api/admin/trades` (`worker/src/routes/admin.js`, `src/components/AdminView.jsx`). **Reports**: the fraud/issue report queue, open ones first, each with a link to view that trade's chat log — see **Trade reports & chat** above. Trades and Reports both exist so an admin can look into a dispute on a user's behalf without needing their login.

**The cards shown for a trade are a snapshot taken at propose time, not a live lookup.** `trade_proposals` itself only ever linked two accounts (see `migrations/0001_initial_schema.sql`) — the cards shown anywhere in the UI came from live haves/wants matching, recomputed fresh on every request. That's fine for browsing matches, but it means a trade's card details would silently change or vanish if either side edited or deleted the underlying `collection_items` afterward — no good for reviewing what a finalized trade actually was. So `proposeTrade` now also computes, server-side, which of the proposer's haves match the recipient's wants and vice versa (same `matchKey` logic as `matches.js`, just narrowed to one pair) and writes a denormalized copy of each into a new `trade_snapshot_items` table (`migrations/0007_trade_snapshots.sql`), inserted atomically with the proposal itself via `env.DB.batch()`. It's computed from the server's own view of each account's collection, never trusted from the client, since a proposal becomes a permanent record. Trades proposed before this feature shipped have no snapshot rows and show "no overlapping cards were recorded" instead of guessing.

**Each snapshotted card's verification photo comes along too** (see **Card verification photos** above for how that's kept independent of the live collection item), viewable through a camera-emoji button on the card the same way it works elsewhere — `GET /api/admin/trade-photos/:snapshotItemId`, admin-only, keyed by the snapshot row's own id rather than the original `collection_items` id.

**Who's an admin is a fixed allowlist in `worker/wrangler.toml`'s `ADMIN_USERNAMES` var (comma-separated usernames), not a database column.** Deliberately not self-service: nothing in the app ever reads or writes admin status to/from a row, so no account — including an admin's own — can grant itself or anyone else admin access by writing data. Changing who's an admin means editing that var and deploying, the same as any other code change; it's checked into git like everything else here, not a runtime secret.

The allowlist match is case-insensitive (`worker/src/admin.js`), unlike username uniqueness/login elsewhere in the app, which stay case-sensitive. This var is hand-typed into a config file rather than looked up, so a casing slip between the deployed value and the account's actual stored username (e.g. `cwinchester636` in the var vs. `Cwinchester636` as signed up) would otherwise silently deny admin access instead of erroring.

**Deleting a user is permanent and explicit-cascade, not FK-cascade.** `collection_items`, `push_subscriptions`, `known_matches`, `local_events`, `event_rsvps`, `notifications`, `account_blocks`, `trade_proposals`, `trade_snapshot_items`, `trade_messages`, `trade_reports`, and `trade_ratings` all declare `ON DELETE CASCADE` on their foreign keys, but SQLite — and by extension D1 — only enforces foreign key constraints when `PRAGMA foreign_keys` is turned on for the connection, which nothing in this codebase does. Rather than depend on that pragma's default (undocumented here either way), `deleteUser` explicitly deletes a target's collection items, push subscriptions, known-match rows (either side — `account_id_a` or `account_id_b`), this account's own event RSVPs, every *other* account's RSVP on an event this account created (deleted before that event row itself, since D1 batches run sequentially in one transaction and those RSVPs would otherwise be orphaned the instant it's gone), posted events, notifications, and block rows naming this account either as blocker or as blocked (`account_blocks`, same either-direction reasoning as everywhere else this feature touches), then everything trade-id-scoped (snapshot items, chat messages, reports, ratings) on every trade either side of them was ever party to, then every one of those trade proposals, then the account row itself, in one `env.DB.batch()` call — scoping the trade-id-scoped deletes by "any trade this account was ever a party to" correctly covers every message they sent, every report they filed, and every rating they left or received too, since all three only ever happen on your own trade.

**Guardrails:** the endpoint refuses to let an admin delete their own account (a 400, with a message pointing at logging out instead) — pure accident-prevention, not a security boundary, since an admin could just remove themselves from `ADMIN_USERNAMES` and redeploy anyway. The account list never includes `token_hash`, `password_hash`, or `password_salt` — nothing in the admin response could ever be used to authenticate as someone else, even by another admin.

## Deploying

Both the API and the frontend auto-deploy via GitHub Actions on every push to `main` (or `claude/simple-app-ideas-1y7kvr`, this branch) that touches their files — `.github/workflows/deploy-worker.yml` for `worker/`, `.github/workflows/deploy-frontend.yml` for everything else (`src/`, `index.html`, `wrangler.jsonc`, `.env`) — or manually via **Actions → (workflow name) → Run workflow**. One-time setup (already done for this deployment):

1. Repo secrets (Settings → Secrets and variables → Actions → **Repository secrets**, not Environment secrets): `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
2. The token needs **four** permissions, not the two you'd guess from Cloudflare's docs — the extra two matter specifically for `wrangler d1 migrations apply --remote`'s auth check:

   | Resource | Item | Permission |
   |---|---|---|
   | Account | Workers Scripts | Edit |
   | Account | D1 | Edit |
   | User | User Details | Read |
   | User | Memberships | Read |

3. A `workers.dev` subdomain registered on the account (one-time, free, done via the Cloudflare dashboard's Workers & Pages onboarding).
4. `actions/setup-node` **must use Node ≥22**. At Node 20, `cloudflare/wrangler-action` silently installs Wrangler 3.x instead of the 4.x this project actually targets, and Wrangler 3.x fails the `/memberships` auth check against a scoped API token in a way that looks identical to a bad token — this cost the most debugging time of anything above, so it's worth calling out on its own.
5. **A local `wrangler` devDependency pin (`"wrangler": "^4.0.0"`) in whichever `package.json` the deploy runs from.** `wrangler-action` only respects a project's own pinned version if one exists; with none, it silently falls back to an old default (3.90.0 in testing) regardless of Node version. That default can't do assets-only deploys at all (fails with "Missing entry-point"), which is exactly what hit the frontend deploy even after the Node fix above — both `worker/package.json` and the root `package.json` need this pin.
6. **Schema changes go through `worker/migrations/`, applied via `wrangler d1 migrations apply swapdeck --remote --config ./wrangler.toml`** (see `deploy-worker.yml`) — not a single hand-idempotent `schema.sql` run on every deploy (the original approach, before trades needed a schema change). Wrangler tracks which migration files have already run in a `d1_migrations` bookkeeping table on the database itself, so re-running the same command on every future deploy only ever applies files it hasn't seen yet — no risk of a second `ALTER TABLE ADD COLUMN` erroring on an already-migrated database.
7. **Every `wrangler` command run against `worker/` needs an explicit `--config ./wrangler.toml`, including `deploy` itself** — this repo is a monorepo with a second `wrangler.jsonc` at the root (for the frontend), and without `--config`, Wrangler 4.135.0 sometimes resolves against the *root* config instead of the one in `workingDirectory`. It first showed up as `d1 migrations apply` reporting "no migrations present" (resolving `migrations_dir` against the repo root); the same run's separate `wrangler deploy` step then failed too, with `The directory specified by the "assets.directory" field ... does not exist: .../dist` — i.e. it had picked up the *frontend's* config (which has an `assets.directory`) instead of the worker's. Both are fixed the same way: pass `--config ./wrangler.toml` explicitly, on every command, every time — don't rely on Wrangler finding the right file in a directory that has more than one config in its tree.
8. **A step-level `if:` conditional referencing the `secrets` context failed the entire workflow before any job started** — the first version of the "Set VAPID private key secret" step used `if: ${{ secrets.VAPID_PRIVATE_KEY != '' }}` to skip itself when that secret isn't set; the resulting run showed the workflow's file path instead of its name and produced zero jobs, which is GitHub's tell for a workflow that failed schema validation rather than one that ran and failed. Fixed by dropping `if:` entirely and doing the skip with a plain `if [ -n "$VAPID_PRIVATE_KEY" ]` inside the step's own `run:` — unambiguous, no reliance on exactly what `if:` does or doesn't support with `secrets`.
9. **Outstanding, not yet done: a `VAPID_PRIVATE_KEY` repo secret for push notifications.** See **Push notifications** above — until this is added, the deploy workflow's "Set VAPID private key secret" step just prints a message and skips itself (harmless), and push sending silently no-ops (also harmless — everything else works normally, notifications just never arrive). Add it once at Settings → Secrets and variables → Actions → **New repository secret**, name `VAPID_PRIVATE_KEY`.

The frontend is a plain static-assets Worker (`wrangler.jsonc`, no `main` script, no bindings) built from `dist/` — Cloudflare's own guidance for this is `migrate_pages_to_workers_guide` (Pages is legacy; this is the current recommended path for a project with no server-side routes). The API's URL needs to be set as `VITE_API_BASE_URL` before building the frontend — already done here via a committed `.env` (see **Accounts & auth** — this value isn't a secret, the client has to know it regardless, so per Vite's convention it's checked in rather than left as a local-only override).

## Custom domain

`swapdeck.cards` is configured declaratively in `wrangler.jsonc` (`routes: [{ pattern: "swapdeck.cards", custom_domain: true }]`) rather than as a manual dashboard step, so it deploys through the same CI pipeline as everything else. Two things worth knowing if you change or add to this:

- **It needs one more token permission beyond the table above:** `Zone → Workers Routes → Edit`, scoped specifically to the `swapdeck.cards` zone. The account-level permissions that cover everything else don't cover this — it's zone-scoped, not account-scoped.
- **Adding a custom domain silently disables the `workers.dev` URL** unless `workers_dev: true` is explicitly set in `wrangler.jsonc` (confirmed via the deploy log: `Because 'workers_dev' is not in your Wrangler file, it will be disabled for this deployment by default`). `swapdeck.cwinchester636.workers.dev` is no longer reachable as a result — `swapdeck.cards` is the only public URL for the frontend now.
- Requires the domain to already be an active Cloudflare zone (automatic if bought through Cloudflare's own registrar, as this one was; otherwise the domain needs adding to Cloudflare with a nameserver change first).

## Privacy policy

`public/privacy.html` — a real, honest description of what SwapDeck actually collects (account info, ZIP-derived approximate location, collection/trade data, verification photos) and doesn't (no ad trackers, no precise GPS, no selling data), not boilerplate. It's a plain static HTML file rather than a React route deliberately — this app has no client-side router at all (`App.jsx` switches views on local `tab` state, not URLs), so a page that needs to work as a stable, linkable URL independent of the SPA is simplest as a file `public/` already serves as-is. Deployed at `https://swapdeck.cards/privacy.html` through the same CI pipeline as everything else (`public/**` is already a `deploy-frontend.yml` trigger path). Linked from the signup screen (`Onboarding.jsx`) and from Profile, so it's reachable both before and after creating an account — this matters beyond just being good practice: Google Play's app review specifically checks that a listed privacy policy URL is actually reachable *from within the app*, not just present in the Play Console listing.

**Contact address is `support@swapdeck.cards`, which needs one manual one-time setup step to actually receive mail**: Cloudflare's free Email Routing (Cloudflare dashboard → the `swapdeck.cards` zone → Email → Email Routing → add a routing rule forwarding `support@swapdeck.cards` to a real inbox) — not something achievable through the Workers/D1 APIs already used elsewhere in this project, and not yet done as of writing.

## Mobile app (Capacitor)

The same React app also builds into real iOS and Android app-store apps via [Capacitor](https://capacitorjs.com/) — not a rewrite, a native shell (`android/`, `ios/`) that loads the exact same `dist/` bundle Vite already produces for the web deploy, so every feature above (trades, matches, events, blocking, etc.) works identically without a second implementation. This exists specifically as groundwork for **in-app purchases** — Apple/Google both require their own billing (StoreKit / Play Billing) for anything sold *inside* a native app, and that only exists once there's a real native app to put it in. What actually gets gated behind a paid tier is a separate, later decision; this is just the shell.

**appId is `cards.swapdeck.app`, appName is "SwapDeck"** (`capacitor.config.json`) — the reverse-DNS-style id every store submission is permanently keyed to once published, so it's worth getting right before then, but freely changeable up until an actual store submission. `webDir` is `dist`, the same Vite build output already used for the Cloudflare Pages-style deploy.

**Icons and splash screens are generated, not hand-drawn**, from the existing purple/gold `public/favicon.svg` mark: `assets/icon-only.png` and `assets/splash.png` (1024×1024 and 2732×2732 source renders, made via `sharp`) are the source of truth, and `npx capacitor-assets generate` fans them out into every density Android and iOS each need — adaptive icon foreground/background layers, round icons, light/dark splash variants, all wired into `AndroidManifest.xml`'s `android:icon`/`android:roundIcon` and the `Theme.SplashScreen` style on Android, and into `Assets.xcassets` plus `LaunchScreen.storyboard` on iOS — both platforms show a real branded launch screen with zero extra plugin, since both native templates already reference these resource names by default. Re-run that same generate command (with `--iconBackgroundColor`/`--splashBackgroundColor` flags matching the app's own `#f4f1fb` background) any time the source mark changes.

**It talks to the same production API the website does, unchanged.** The native bundle is built the normal way (`npm run build`), which bakes in `VITE_API_BASE_URL` from the committed `.env` — already the live Worker (`https://swapdeck-api.cwinchester636.workers.dev`), not `localhost`, so a device running this app hits the real backend immediately. This works with zero backend changes because `CORS_HEADERS` (`worker/src/utils.js`) already allows every origin (`Access-Control-Allow-Origin: '*'`) — necessary in the first place for the plain web app itself, and it happens to also cover a Capacitor app's internal WebView origin with nothing extra to configure.

**`npm run cap:sync` is the one command to run after any frontend change** meant for the native apps — it's `vite build` followed by `cap sync`, which copies the fresh `dist/` into both `android/app/src/main/assets/public` and `ios/App/App/public` and updates each platform's plugin registration. `npm run cap:open:android` / `npm run cap:open:ios` do that sync and then launch Android Studio / Xcode on the project. Both native project directories are committed to the repo (the standard Capacitor convention — unlike `node_modules`, they're real project configuration, not a reproducible build artifact) with their own generated `.gitignore`s excluding actual build output (`*.apk`, `.gradle/`, `DerivedData`, `Pods`, etc.).

**What's been verified here vs. what genuinely needs real hardware/tooling this sandbox doesn't have:** `npx cap doctor` reports the Android project healthy end-to-end (dependency versions matched, Gradle project structure sane); the web build correctly copies into both native `public` directories via `cap sync`, confirmed by direct inspection of the copied files; and the generated icon/splash resources are correctly wired into both platforms' native config, confirmed by grepping the actual `AndroidManifest.xml`/`styles.xml` and iOS storyboard/asset-catalog references rather than assuming the generator did its job. **What couldn't be verified from here, and why:** this is a Linux sandbox with no Xcode (`xcodebuild` doesn't exist — iOS app builds and simulator runs are only ever possible from a real Mac, there's no workaround), and while Java + Gradle are present, there's no Android SDK installed and no way to install one — `dl.google.com` (where `sdkmanager` fetches the SDK from) is blocked by this sandbox's outbound network policy (confirmed via the agent proxy's own status endpoint reporting a `connect_rejected` on that exact host), the same class of blocked-domain limitation already hit and documented for `fcm.googleapis.com` and the live card-search APIs elsewhere in this file. So an actual compiled `.apk`/`.ipa`, an app launching on a real device or emulator, and a real API call succeeding from inside the native shell all remain unverified — genuinely likely to work, given `CORS_HEADERS` already being wide open and the web bundle being unchanged, but "likely" isn't "confirmed," and this file doesn't claim more than what was actually checked anywhere else either.

**Real next steps, none of which can happen from this sandbox:** open `android/` in Android Studio (or run `./gradlew assembleDebug` on a machine with the Android SDK) to get a real installable `.apk`; open `ios/App/App.xcworkspace` in Xcode on a Mac, which needs an Apple Developer account ($99/year) for device builds and any App Store submission; and, for the Android side of real purchases, the external Google Play Console / RevenueCat setup checklist in **In-app purchases** below — the RevenueCat-backed purchase code itself is already built.
